          - heading "Summary" [level=2] [ref=e2515]
          - paragraph [ref=e2516]: The guide comes down to four layers.
          - generic [ref=e2517]:
            - term [ref=e2518]: The component
            - definition [ref=e2519]: Can I build it correctly?
            - term [ref=e2520]: The API
            - definition [ref=e2521]: Can other engineers use it correctly, without reading how it works?
            - term [ref=e2522]: The platform
            - definition [ref=e2523]: Can many teams depend on it safely, over years, while it keeps changing?
            - term [ref=e2524]: The organization
            - definition [ref=e2525]: Can I improve the decisions, standards, tools, and people that keep the platform healthy?
          - paragraph [ref=e2526]: Senior UI engineering tends to be strongest in the first two. Staff UI-platform engineering increasingly operates in the second and third. Principal scope reaches the fourth. Real companies draw those boundaries differently, so treat it as a thinking tool rather than a ladder to climb.
          - paragraph [ref=e2527]: A Staff-level UI engineer does more than build the hardest dropdown, valuable as that is. They ask how the component should behave, how its API should behave, how product teams will consume it, how it stays accessible, how it gets tested, how it is packaged, how changes ship safely, how teams migrate, how designers and engineers stay aligned, how anyone will know whether the system is working, and how the next engineer ends up more effective than the last one.
          - paragraph [ref=e2528]: The transition is from building UI to engineering the platform through which an organization builds UI.
